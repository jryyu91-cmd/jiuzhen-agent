# 酿见 AI · 中小酒企的 AI 营销大脑

> 2026 多彩贵州·贵客松 | 传统行业 AI 解决方案 | AI × 白酒

**一句话：把酒厂已有的散乱资料，变成会找消费者、会找场景、每句话有依据的营销资产。**

品牌 Slogan：**先看见消费者和生活场景，再决定这瓶酒怎么卖。**

## 它不是什么

酿见不是“输入几个关键词，生成三篇白酒文案”的工具。

真正想解决的是中小酒企进入消费者直连阶段后的一整条工作链：

- 产品资料散在 PDF、瓶身、招商资料、微信和历史内容里；
- 市场人员未必能先回答“目标人群是谁、消费场景是什么”；
- 同一个事实在不同渠道反复整理，容易写错、夸大或丢失来源；
- 公众号、朋友圈、短视频都要做，但人少，无法持续做判断、执行和复盘；
- 没有一套会随着使用不断沉淀的品牌营销记忆。

酿见的产品原则是：**不要让企业适应 AI，要让 AI 适应企业已有的工作方式。**

## 核心链路

```text
企业已有资料
PDF / 产品手册 / 历史内容 / 零散文字
        ↓
资料理解
        ├─ 产品 / 价格 / 度数 / 规格 / 产区
        ├─ 事实来源与原文片段
        └─ 缺失字段提示
        ↓
人工只确认缺口
        ↓
酒厂营销记忆（一厂一档）
        ↓
营销诊断
        ├─ 优先成年消费者
        ├─ 场景机会
        ├─ 判断依据
        └─ 下一步小范围测试
        ↓
公众号 / 朋友圈 / 短视频
        ↓
事实核验 + 酒类营销风险检查
        ↓
评论 / 私域承接
        ↓
未来：真实经营数据回流，继续修正下一轮判断
```

## 1. 资料先行，不先填营销表

工作台第一步不是要求用户填写“目标人群、品牌定位、消费场景”。

用户可以直接上传：

- PDF 文本版；
- TXT / Markdown；
- CSV / JSON；
- 或者直接粘贴老板、销售、产品资料中的一段文字。

当前 Demo 会先提取：

- 酒厂 / 品牌；
- 产品名；
- 价格；
- 酒精度；
- 规格；
- 产区；
- 已出现的工艺/产品事实；
- 可复用的真实场景素材。

每条硬事实尽量保存：**事实值 + 来源文件 + 原文片段**。

扫描件、图片、语音、微信转发、企业知识库属于后续输入形态；产品架构已经按“多入口、同一个营销大脑”设计，不要求用户以后都回到一张网页表单。

## 2. 事实层和营销推断严格分开

这是酿见非常重要的边界。

资料层只能回答：

> “这家企业的资料里明确写了什么？”

营销层才回答：

> “基于这些已确认事实，下一轮最值得测试谁、什么场景？”

因此系统不应该因为“酱酒通常如此”就替一家具体酒厂补写：

- 大曲坤沙；
- 自有窖池；
- 某个年份；
- 获奖资质；
- 官方商城；
- 包邮 / 退换承诺。

没有证据就提示缺口，而不是自动补齐。

## 3. 营销诊断是核心，不是附属功能

用户可以不知道“卖给谁”。

酿见会结合价格、已确认度数/规格、企业已有场景、营销目标和现有渠道，先输出：

- 优先成年消费者；
- 购买触发时机；
- 值得验证的生活场景；
- 内容角度；
- 转化动作；
- 推荐渠道；
- 下一步 7-14 天的小范围测试。

当前版本有两种运行方式：

1. **LLM 推理模式**：配置兼容 Chat Completions 的模型后，用大模型完成受品牌事实约束的资料理解与营销推理；
2. **规则兜底模式**：模型不可用时，根据价格、度数、规格、企业输入和已确认事实继续完成可解释诊断，避免现场完全不可用。

模型配置：

```text
LLM_BASE_URL=https://your-provider.example/v1
LLM_API_KEY=***
LLM_MODEL=your-model
```

如果未配置，系统自动使用规则兜底。

## 4. 一厂一档最终不是一张表，而是一套营销记忆

长期产品中的“一厂一档”应该逐步沉淀五类资产：

1. **企业事实**：产区、资质、工艺、历史、渠道；
2. **SKU 事实**：价格、度数、规格、包装、证据；
3. **品牌资产**：语气、禁忌、历史内容、视觉规范；
4. **消费者资产**：谁在买、为什么买、常见问题；
5. **经营反馈**：什么场景、渠道和内容真正带来咨询、成交和复购。

目标是“一次确认，后续复用”，而不是每次打开 AI 都重新填一遍产品资料。

## 5. 内容资产只是执行层

确认策略以后，再生成：

- 公众号；
- 朋友圈；
- 30 秒短视频脚本。

内容层遵循：

- 策略判断不塞进成品；
- 少用“消费者、品牌心智、营销机会”等内部词；
- 从具体生活片段切入；
- 不凭空编亲历、用户评价和品牌事实；
- 酒类内容不展示鼓励饮酒动作；
- 不把饮酒与解压、消愁、功能效果绑定。

## 6. 发布前检查

生成内容继续经过：

1. **事实证据检查**：卖点是否有品牌资料支撑；
2. **酒类营销风险检查**：诱导饮酒、情绪/功能暗示、绝对化宣传等基础风险。

当前规则检查只做风险兜底，不替代企业正式法务审核。

## 7. 产品入口不应该只有网站

长期形态可以是多个轻入口，共用一个营销大脑：

| 入口 | 更适合的任务 |
| --- | --- |
| Web 工作台 | 建档、SKU 管理、完整诊断、内容与数据复盘 |
| 微信小程序 | 拍产品、传资料、临时生成朋友圈、现场问产品问题 |
| 企业微信 / 微信入口 | 直接把文件、语音、聊天内容转给酿见处理 |
| App | 当使用频率和移动工作流成熟后再做，不作为第一阶段前提 |

完整产品路线见 [`docs/产品路线图.md`](docs/产品路线图.md)。

## 10. 当前版本边界

当前是 48 小时原型 / Demo，不把暂未实现的能力包装成已经完成：

- PDF 当前主要支持有文本层的文件，扫描图片还未接 OCR / 视觉模型；
- “一厂一档”目前是演示数据结构，还没有正式企业账号、权限和数据库持久化；
- 历史经营数据尚未接入，因此当前“场景建议”是待验证建议，不是销量因果结论；
- 内容生成目前以稳定规则模板为主，LLM 主要用于可选的资料理解与营销推理；
- 评论承接尚未接企业真实库存、门店、电商和 CRM，因此不会替企业编购买渠道或售后承诺。

## 11. 下一阶段验证

不优先继续增加更多内容渠道，而是找真实中小酒企跑一个最小 PoC：

1. 用企业现成资料完成一次建档；
2. 人工确认事实证据；
3. 选择 2-3 个“人群 × 场景”组合；
4. 连续测试 2-4 周；
5. 回收阅读、咨询、到店/下单、复购等数据；
6. 让真实经营反馈反过来调整下一轮营销建议。

真正要验证的问题不是“AI 能不能写白酒文案”，而是：

> **一个没有完整市场团队的中小酒企，会不会愿意把酿见留在日常工作里继续用。**
